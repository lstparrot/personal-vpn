# План: личный self-hosted VPN с выходом через США

Дата: 7 октября 2026. Статус: серверная автоматизация и управление профилями реализованы локально; VPS ещё не выбран и живое развёртывание не проверено. Выборочный режим и строгий kill switch остаются в разработке.

## 1. Цель и рамки

Развернуть воспроизводимый VPN для личных устройств на арендованном VPS в США. В обычном режиме весь интернет-трафик подключённого устройства выходит через публичный адрес VPS. После замены VPS конфигурацию можно восстановить из репозитория и защищённого хранилища ключей.

**Подтверждённые параметры:** один сервер, 1–5 личных устройств на Windows и macOS, расчётный объём 1 ТБ/мес. при небольшом бюджете; клиенты подключаются в основном из стран СНГ. По умолчанию весь трафик идёт через США. Дополнительно нужен режим, в котором **Claude Desktop, Claude Code в терминале, Cursor и его локальный Agent** ходят через VPN и не выходят напрямую при его потере, а прочие приложения могут использовать обычный Интернет. Установка и включение должны быть быстрыми; желательно использовать готовый клиент, без разработки отдельного приложения. Проект планируется выпустить с открытым исходным кодом. Пока неизвестна верхняя граница месячных расходов.

**Вариант бесплатного VPS:** Oracle Cloud Always Free подходит по заявленному трафику, но стандартный образ OCI содержит обязательные правила firewall для загрузочного тома. Текущий playbook заменяет ruleset и не должен запускаться на OCI до отдельной адаптации и живой проверки. Порядок регистрации и создания VM приведён в `docs/ORACLE.md`.

**Важное ограничение:** выделенный VPS даёт собственный выходной IP, но не гарантирует «чистоту» адреса, доступ к каждому сайту или видимость как домашнего пользователя США. Сервисы могут учитывать ASN дата-центра, репутацию адреса, историю входов и другие сигналы. Задача проекта — управляемый американский выходной узел и проверка пригодности IP для конкретных нужных сервисов, а не обещание обхода любой блокировки.

## 2. Решение

```text
Устройство ── зашифрованный WireGuard/UDP ── VPS в США ── NAT/маршрутизация ── Интернет
                 DNS через туннель          │
                                            └── DNS-сервис, доступный только из VPN
```

| Компонент | Выбор для v1 | Почему |
| --- | --- | --- |
| VPN | WireGuard из пакетов поддерживаемой Ubuntu Server LTS | Небольшая конфигурация, готовые клиенты для Windows и macOS, без отдельного control plane |
| Хост | Один VPS в США с публичным выделенным IPv4, SSH-доступом, консолью восстановления и не менее 1 ТБ включённого исходящего трафика | Простой исходный вариант и контролируемый счёт |
| Автоматизация | Ansible с конфигурацией в Git | Повторяемая установка и управляемые изменения |
| Сеть | Полный туннель, отдельный адрес на каждый peer, NAT для IPv4 | Все устройства используют выходной IPv4 VPS |
| DNS | Локальный резолвер на VPS, доступный только из туннеля | DNS-запросы идут через VPN; нет открытого DNS-сервера в Интернете |
| Администрирование | SSH по ключам; клиентские ключи хранятся вне Git | Нет публичной админ-панели и паролей в репозитории |
| Firewall | Одна управляемая система правил; разрешены SSH и порт WireGuard/UDP | Предсказуемая политика входящего и пересылаемого трафика |

Выбираем нативный WireGuard и системный сервис `wg-quick@wg0`. Контейнеры и веб-панель в v1 не нужны: они не улучшают качество выходного IP, но добавляют обновления, права доступа и потенциально открытые порты. Ansible на машине администратора подключается по SSH и настраивает сервер; постоянно работающий управляющий сервис не требуется. Серверная конфигурация одинаковая для полного и выборочного режимов: выбор приложений и kill switch реализуются на **клиентском устройстве**, потому что сервер не знает, какой процесс создал пакет.

**Простой сценарий v1:** владелец запускает установку сервера; проект создаёт отдельный профиль для каждого устройства; на Windows/macOS пользователь устанавливает официальный клиент WireGuard, один раз импортирует профиль и затем включает/выключает туннель в нём. Собственное графическое приложение не требуется. Профиль и закрытый ключ передаются безопасно, не через публичный репозиторий. Если из конкретной сети обычный WireGuard не проходит, выбирать и проверять альтернативный клиент/транспорт на основании испытаний из этой сети.

### Режимы трафика и границы платформ

| Режим | Поведение | Требование к kill switch |
| --- | --- | --- |
| Полный туннель — стандарт | Все приложения через VPS | Если нужен строгий режим, клиентская ОС блокирует прямой выход при потере туннеля |
| Выбранные приложения | Выбранные приложения через VPS, остальные напрямую | Выбранные приложения не получают сеть, пока VPN недоступен |
| Исключённые приложения | Все через VPS, кроме заданных исключений | Исключения сознательно идут напрямую; остальные блокируются при отказе туннеля |

**Windows:** официальный клиент WireGuard включает общесистемный kill switch при полном маршруте `/0`. Он не является правилом для выбранных приложений. По текущей документации AmneziaVPN выбор по приложениям в Windows работает только как исключение: отмеченные программы идут *мимо* VPN; режим «только отмеченные через VPN» недоступен. Строгий выборочный режим потребует дополнительного локального компонента и правил Windows Filtering Platform, связанных с приложением и интерфейсом, плюс тестов DNS, IPv6, смены пути исполняемого файла и восстановления правил после сбоя.

**macOS:** AmneziaVPN сейчас документирует выбор только по IP/подсетям, не по приложениям. Строгая привязка произвольной программы к VPN требует локального клиента/системного расширения с Network Extension или другого проверенного механизма на устройстве. Серверный профиль WireGuard сам по себе этого сделать не может. Подписывание и установка системного расширения увеличивают сложность открытого релиза.

**Вывод для продукта:** без локального клиента или помощника на Windows и macOS нельзя обещать произвольный выбор приложений с fail-closed поведением. Предпочтение «без отдельного приложения» применимо к первому релизу с полным туннелем: один готовый VPN-клиент, импорт профиля, переключатель подключения. Для выборочного режима сначала проверить конкретные нужные приложения: если они сами поддерживают прокси и строго не обходят его при отказе, возможна лёгкая настройка для этих приложений. Для произвольных программ запланировать небольшой открытый локальный компонент без отдельной веб-панели; он может устанавливаться одним пакетом, но будет системным ПО и потребует проверки прав и обновлений.

**Прицельный вариант для Claude Desktop и Cursor:** исследовать один готовый локальный маршрутизатор с TUN и правилами по имени/пути процесса, например sing-box. Его документация заявляет правила `process_name`/`process_path` для Windows и macOS и WireGuard endpoint. Прототип должен направлять процессы Claude/Cursor через VPS, остальные — напрямую, а запросы выбранных процессов при недоступности WireGuard — отклонять. Проверить обе платформы на реальных сборках. Это может дать удобное управление без разработки собственной графической программы, но **правило маршрутизатора само по себе не является строгим kill switch**: при остановке маршрутизатора или исчезновении TUN ОС может вернуть обычный маршрут. Для релизного обещания fail-closed потребуется независимое постоянное правило ОС либо доказанное системное поведение клиента. На Windows кандидатом служат постоянные правила firewall для исполняемых файлов и физических интерфейсов; на macOS — системный Network Extension filter либо другой проверенный механизм. Не считать конфигурацию прокси внутри редактора заменой такой защиты.

**Политика процессов для первого прототипа:** защищать сетевые соединения самого Claude Desktop и его локальных функций, отдельно запущенного Claude Code CLI, редактора Cursor и его локального Agent. Для CLI сделать явную команду запуска через защищённый режим, чтобы не направлять через VPN любой процесс с общим именем интерпретатора. Терминальные команды, которые Claude Code или Cursor запускают как инструменты, включать в гарантию только после проверки процесса-наследника и его маршрута. Для каждого приложения проверить вход в аккаунт, чат, потоковые ответы, обновления, расширения/MCP и запросы по IPv4/IPv6/DNS.

**Граница облака:** Cursor Cloud Agents исполняются на инфраструктуре Cursor и используют её сетевой выход; локальный VPN этого не меняет. Claude Desktop также позволяет запускать локальные и облачные Code-сессии. Обещание «IP нашего VPS» относится к локальному сетевому трафику защищённых программ и локальных сессий; для облачных задач нужна отдельная конфигурация среды выполнения, которая не входит в первый релиз. Проверка должна фиксировать реальные локальные процессы и их исходящие соединения.

Публичный релиз с полным туннелем гарантировать на Windows и macOS **только в сетях, где выбранный транспорт проходит проверки**. Выборочный режим считать отдельным релизным требованием, а не уже обеспеченной функцией WireGuard/AmneziaVPN; матрицу поддержки публиковать по фактически пройденным испытаниям.

### Доступность из стран СНГ

До окончательного выбора протокола провести пробное подключение из реальных домашних и мобильных сетей клиентов. Обычный WireGuard работает поверх UDP и может не проходить в части сетей. Если это подтверждается, предусмотрен отдельный транспортный профиль и модуль автоматизации: проверить актуальный AmneziaWG на том же VPS и тех же клиентских ОС. По документации проекта версия 3.1 создана после блокировок прежних версий в России; это **кандидат для теста**, а не обещание устойчивой работы в любой сети. Для AmneziaWG отдельно проверить совместимость клиентов, обновления сервера, лицензию зависимостей и те же сценарии утечек/kill switch. Не включать резервный протокол автоматически без фактического теста и требований конкретных сетей.

### IPv6

Решение о IPv6 принимается **до выдачи клиентских профилей**:

1. Предпочтительно получить от провайдера рабочую схему маршрутизации IPv6 к VPS и проверить её. Тогда настроить адреса и правила для каждого клиента, полный маршрут `::/0`, DNS и тест выхода через IPv6 VPS.
2. Если провайдер не даёт надёжной маршрутизации IPv6, клиентский профиль всё равно направляет `::/0` в туннель, а сервер явно не выпускает IPv6 наружу. Это ограничит доступ к IPv6-only ресурсам, но позволит избежать прямого выхода клиента через его местный IPv6 в проверенных приложениях. Проверки утечек выполняются на каждой целевой ОС. Нельзя считать строку `::/0` универсальным системным kill switch: поведение при отключении туннеля зависит от клиента и ОС.

## 3. Требования к VPS и проверка IP

**Обязательно:** физический/сетевой регион США, публичный выделенный IPv4 без CGNAT, возможность открыть UDP-порт, root/sudo через SSH, штатная консоль провайдера для восстановления доступа, поддерживаемая Ubuntu Server LTS, понятный лимит исходящего трафика и условия использования. Нужны снапшоты или резервные копии, API провайдера желателен для будущей автоматизации.

**Стартовая оценка ресурсов, не гарантия производительности:** 1 vCPU, 1–2 ГБ RAM и 15–25 ГБ диска для 1–5 клиентов. Расчётный объём — **1 ТБ/мес.**; при выборе тарифа лучше иметь запас сверх этого объёма на накладные расходы VPN и рост использования. Сравнивать включённый **исходящий** трафик, цену превышения, ограничение порта и качество маршрута из фактического местоположения клиентов; CPU и диск обычно вторичны. Проверить, не запрещает ли тариф длительную высокую нагрузку или VPN-сценарии. Задержку до США измерить из сетей будущих клиентов.

**Кандидат для ценового сравнения, без решения о покупке:** Hetzner Cloud в Ashburn, Virginia. У провайдера есть также Hillsboro, Oregon, но для клиентов из СНГ восточное побережье США логично проверить первым; фактический маршрут надо измерить. По документации Hetzner включённый трафик у облачных тарифов в США зависит от плана и находится в диапазоне 1–5 ТБ/мес.; исходящий сверх лимита оплачивается отдельно. Для цели 1 ТБ/мес. сравнить начальный тариф с тарифом, у которого есть запас по трафику, и учесть отдельную плату за публичный IPv4. Цены и квоты проверить на странице заказа непосредственно перед оплатой.

**При приёмке конкретного VPS:** проверить адрес, ASN, заявленную геолокацию в нескольких базах и доступ к 2–3 действительно нужным сервисам; затем измерить задержку, скорость, потери пакетов и отсутствие блокировки UDP из своей сети. Для «чистого IP» нужна проверка реального адреса после выдачи: заранее гарантировать это по названию провайдера или тарифу нельзя. Если адрес не подходит, использовать возврат/замену в рамках условий провайдера.

Пока нужные сервисы не названы, предложить такой минимальный набор проверок: **(а)** посмотреть IP, страну и ASN через IPinfo; **(б)** сравнить видимый IP/страну через независимый сайт и проверить DNS/IPv6 утечки на устройстве; **(в)** открыть именно тот сервис, ради которого нужен выход через США, и выполнить в нём обычное действие. Первые два теста проверяют маршрут и классификацию IP, но не гарантируют доступ к третьему.

## 4. Функциональные требования

1. **Установка:** на новый VPS с известным IP и SSH-ключом выполняется одна документированная процедура; повторный запуск не ломает работающую конфигурацию.
2. **Маршрутизация:** клиентский профиль по умолчанию отправляет весь IPv4-трафик через VPN (`0.0.0.0/0`); политика IPv6 определена как выше.
3. **DNS:** профили указывают DNS-сервис VPS; запросы клиентов не направляются к DNS локальной сети после подключения.
4. **Клиенты:** отдельная пара ключей и VPN-адрес на каждое из 1–5 устройств; добавление, отзыв и пересоздание профиля документированы и автоматизированы.
5. **Выбор приложений:** опубликованная матрица по ОС отдельно показывает полный туннель, выбор приложений, исключение приложений и строгое блокирование при обрыве. Функция считается реализованной только после проверки, что выбранное приложение не уходит напрямую при остановке VPN-процесса, обрыве UDP и перезагрузке устройства.
6. **Доступ:** клиентские устройства не получают доступ к SSH VPS; общение между клиентами по умолчанию запрещено.
7. **Сохранность:** сервер поднимает туннель после перезагрузки; правила firewall и маршрутизации сохраняются.
8. **Наблюдаемость:** доступны статус сервиса, время последнего handshake, объём передачи, доступность DNS и внешний IP; авария обнаруживается мониторингом. Предупреждение о приближении к лимиту трафика обязательно.
9. **Восстановление:** новый VPS можно подготовить из Git и резервной копии секретов; процедура замены IP и обновления клиентских профилей описана.

## 5. Требования безопасности и эксплуатации

- SSH только по ключам; парольный вход и вход root по SSH отключены после проверки отдельной учётной записи и консоли восстановления. Доступ по SSH ограничить доверенными адресами, если они стабильны; иначе использовать ключи и rate limiting.
- Закрыть все входящие порты, кроме SSH и выбранного UDP-порта WireGuard. DNS слушает только loopback/VPN-интерфейс. Ограничить пересылку пакетов: VPN → Интернет разрешено, VPN → административные сервисы и peer → peer запрещено.
- Серверный закрытый ключ остаётся на VPS с правами только владельца. Клиентские закрытые ключи генерируются и выдаются по одному устройству, хранятся в защищённом хранилище вне Git. Задачи автоматизации, работающие с секретами, не печатают их в лог.
- Ключ потерянного устройства отзывается удалением peer на сервере и выпуском нового профиля. После компрометации сервера заменить серверный и клиентские ключи.
- Включить автоматические обновления безопасности ОС, контролировать перезагрузки, регулярно проверять доступность туннеля. Не включать журналирование DNS-запросов и содержимого трафика без отдельной необходимости; системные и провайдерские журналы остаются отдельной частью модели доверия.
- Сделать резервную копию зашифрованных секретов, инвентаря peer и инструкции восстановления. Проверить восстановление на новом VPS, а не полагаться только на снапшот старого.
- На клиенте по возможности включить функцию блокировки трафика при потере VPN в штатном приложении/ОС. Это отдельная клиентская настройка и отдельный тест, сервер её не обеспечивает.

Для личного проекта Terraform/аналог нужен только если выбранный провайдер имеет стабильный API и серверы планируется часто менять. На первом этапе покупка VPS вручную, а настройка ОС через Ansible даёт достаточную воспроизводимость. Покупку и выдачу IP автоматизировать после выбора провайдера.

### Требования к открытому релизу

- В Git публиковать только код, шаблоны и вымышленные примеры. Проверить историю и каждый релиз на приватные ключи, клиентские профили, реальные IP/домены, SSH-ключи, токены провайдера, пароли Ansible Vault и адреса электронной почты. Реальные конфигурации пользователя хранить отдельно от публичного репозитория.
- Добавить `LICENSE` до публикации. **Предварительный выбор — Apache-2.0** для собственного кода автоматизации и клиентских помощников: разрешает использование и модификацию, включает явное патентное разрешение. Перед добавлением стороннего кода проверить совместимость его лицензии; системный WireGuard устанавливается как внешняя зависимость и не копируется в репозиторий.
- В `README` дать быструю установку, поддерживаемые ОС и режимы, ограничения IP и kill switch, стоимость трафика, список открытых портов, восстановление и удаление сервера. Команды должны работать на чистом VPS без ручного редактирования секретов в файлах проекта.
- Для PR включить проверку синтаксиса Ansible, lint, проверку секретов и тест повторного запуска на временной машине. Не запускать непроверенные PR с доступом к секретам и реальному VPS.
- `SECURITY.md` должен описывать приватный канал сообщения об уязвимости и политику исправлений. Перед публикацией провести отдельный аудит секретов и инструкций.

## 7. Этапы реализации

| Этап | Результат | Проверка |
| --- | --- | --- |
| 0. Уточнить параметры | Названия 2–3 приложений для выборочного режима, 2–3 нужных сервиса, потолок расходов | Заполненный чек-лист требований |
| 1. Выбрать VPS | Тариф, регион, выделенный IPv4, способ восстановления, проверенный тестовый IP | SSH и UDP доступны, IP подходит нужным сервисам |
| 2. Собрать автоматизацию | Роли Ansible для ОС, firewall, WireGuard, DNS и выдачи peers | Повторный запуск не меняет исправную систему и не теряет доступ по SSH |
| 3. Выпустить первый профиль | Один тестовый клиент с полным туннелем | Handshake, выходной IP США, DNS через VPS, отсутствие утечек IPv6 |
| 4. Проверить устойчивость | Перезагрузка, отзыв peer, замена ключа, отказ DNS, краткий разрыв туннеля | Предсказуемое восстановление и клиентское поведение |
| 5. Ввести в эксплуатацию | Профили для устройств, резервная копия, мониторинг, инструкция | Все целевые устройства и сервисы проходят приёмку |
| 6. Выборочный режим | Прототип для конкретных программ на Windows и macOS; если настройки приложений недостаточны — локальный системный помощник | Тесты обрыва, перезагрузки, DNS и IPv6 для выбранных и остальных приложений |
| 7. Открытый релиз | Лицензия, инструкции, CI, политика безопасности, очистка секретов | Установка сторонним пользователем на чистом VPS; аудит репозитория и истории |

Оценка трудозатрат: серверный прототип при готовом VPS — примерно 1–2 дня на автоматизацию и 0,5–1 день на клиентские проверки. Публичный релиз с документацией, тестами и аудитом потребует дополнительного времени. Выборочный режим с настоящим kill switch на Windows и macOS — отдельная задача, срок которой зависит от конкретных приложений и результатов прототипа. Доступность и репутация IP зависят от провайдера.

## 8. Критерии готовности

- На каждом поддерживаемом устройстве внешний IPv4 при подключении совпадает с IPv4 VPS; при отключении возвращается обычный адрес.
- DNS-запросы при подключении идут к настроенному DNS через VPN; тесты DNS leak и IPv6 leak пройдены на каждой ОС.
- Проверены нужные пользователю сайты и сервисы именно с выданного IP, включая повторную проверку после перезагрузки VPS.
- После перезагрузки сервер сам поднимает VPN; новая установка и повторный запуск Ansible проходят без ручной правки.
- Потерянный peer удаляется и больше не проходит handshake; новый профиль работает.
- Внешнее сканирование показывает только предусмотренные порты; DNS не открыт наружу.
- Есть резервная копия секретов и проверенная инструкция восстановления на другом VPS.
- Поведение при обрыве VPN проверено на клиентах: если нужен строгий kill switch, трафик не выходит напрямую при разрыве.
- Для выборочного режима подтверждено, что **Claude Desktop, отдельно запущенный Claude Code CLI, Cursor и его локальный Agent** теряют сеть при отказе VPN, а остальные приложения ведут себя согласно описанному режиму; проверены IPv4, IPv6, DNS, перезапуск клиента и ОС. Дочерние инструменты включаются в гарантию только после отдельной проверки. Облачные задания явно исключены из обещания выходного IP VPS.
- Публичный репозиторий содержит лицензию, инструкции и политику безопасности; в нём и в истории нет рабочих секретов.

## 9. Риски и решения

| Риск | Решение |
| --- | --- |
| IP VPS уже имеет плохую репутацию или определяется как дата-центр | Проверять конкретный IP и нужные сервисы в период возврата; предусмотреть смену VPS/IP |
| UDP недоступен в части клиентских сетей | Сначала замерить доступность; если проблема подтверждена, отдельно спроектировать резервный транспорт/узел |
| Утечка IPv6 или DNS | Полные маршруты, управляемый DNS, отдельные проверки на каждой ОС; строгий режим блокировки трафика на клиенте при необходимости |
| Потеря SSH после изменения firewall | Вносить правила через автоматизацию только с проверенной консолью провайдера и откатом; SSH проверить до отключения паролей |
| Компрометация ключа устройства | Индивидуальный peer, быстрый отзыв и перевыпуск |
| VPS недоступен | Мониторинг, резервная копия, инструкция восстановления и при необходимости второй узел в следующем релизе |

## 10. Решения, которые нужны перед закупкой

1. Помимо Claude и Cursor, есть ли сайты/сервисы, ради которых важен американский IP? До этого «чистый» означает корректную геолокацию США, отсутствие очевидной плохой репутации и рабочий локальный доступ к Claude/Cursor; это неполная проверка.
2. Каков максимальный месячный платёж за VPS с учётом IPv4, превышения квоты и резервных копий?
3. Должны ли остальные приложения в выборочном режиме продолжать ходить напрямую при обрыве VPN? Это определяет политику kill switch.
4. Есть ли конкретные сети, где WireGuard/UDP уже не работает?
